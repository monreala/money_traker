# Таверна у Иваныча — материалы для защиты

Подробное описание архитектуры, технических решений и потенциальных вопросов с ответами. Используй для подготовки и как «шпаргалку» во время защиты.

---

## 1. О проекте в одном абзаце

Веб-приложение для управления рестораном «Таверна у Иваныча». Решает 5 ключевых задач: приём заказов официантами (POS), отображение заказов на кухонных дисплеях в реальном времени (KDS), складской учёт с автоматическим списанием ингредиентов по технологическим картам, резервирование столов с проверкой конфликтов и управление сотрудниками с учётом смен. Доступ распределён по 4 ролям: ADMIN, WAITER, CHEF, BARTENDER. Развёртывается одной командой `docker compose up`.

## 3. Архитектура (многослойная)

```
┌─────────────────────────────────────────────┐
│  UI Layer (Vaadin Views)                    │ ← LoginView, POSView, KitchenView, 6 admin views
├─────────────────────────────────────────────┤
│  Service Layer (@Service, @Transactional)   │ ← OrderService, KitchenService, InventoryService...
├─────────────────────────────────────────────┤
│  Repository Layer (Spring Data JPA)         │ ← OrderRepository, *Repository extends JpaRepository
├─────────────────────────────────────────────┤
│  Domain Layer (@Entity)                     │ ← Order, OrderItem, Employee, Ingredient... (15 entities)
└─────────────────────────────────────────────┘
                          │
                          ▼
                   ┌─────────────┐
                   │  MySQL 8.4  │
                   └─────────────┘
```

**Правила:**
- UI вызывает только сервисы (никогда напрямую репозитории)
- Сервисы вызывают репозитории и оперируют сущностями
- Сущности — POJO с JPA-аннотациями, без бизнес-логики (кроме мелких хелперов вроде `Order.recalcTotal()`)
- Транзакции открываются на сервисном слое через `@Transactional`

**Дополнительный модуль** — `security` (Spring Security конфиг, UserDetailsService, SecurityService) и `data` (DataInitializer для стартовых данных при первом запуске).

## 4. Ключевые бизнес-сценарии

### 4.1. Сценарий «Гость пришёл, заказ, оплата»

1. **Официант** заходит как `waiter/waiter` → попадает на POSView (`/`)
2. Видит сетку из 8 столов, цвет = статус (зелёный — свободен, оранжевый — занят, синий — резерв)
3. Кликает по свободному столу → `OrderService.openOrCreate()` создаёт `Order` со статусом OPEN, ставит столу статус OCCUPIED, открывается `OrderDialog`
4. Выбирает категорию (Бар/Горячий цех/Холодный цех) → видит кнопки блюд только из этого цеха
5. Кликает по блюду → `OrderService.addItem()`:
   - Создаёт `OrderItem` со статусом NEW
   - Привязывает к Order
   - Пересчитывает `totalAmount`
   - Бросает событие `ITEM_CREATED` в `KitchenBroadcaster`
6. **Повар** (`chef/chef`) сидит на KitchenView, видит карточку блюда (broadcaster через WebSocket push)
7. Кликает «Готовлю» → статус NEW → COOKING
8. Кликает «Готово» → статус COOKING → READY → событие `ITEM_READY` → у официанта всплывает уведомление «Готово блюдо на кухне»
9. Когда официант забрал блюдо, кликает «Оплатить наличными/картой» → `OrderService.pay()`:
   - Создаёт `Payment`
   - Если суммарная оплата ≥ totalAmount → закрывает заказ (PAID), освобождает стол (FREE)
   - Шлёт `ORDER_PAID` event
10. Сетка столов в POS перерисовывается — стол снова зелёный

### 4.2. Сценарий «Приёмка накладной + автопересчёт себестоимости»

1. Admin заходит в Накладные → «Новая накладная»
2. Выбирает поставщика, вводит номер, добавляет позиции (ингредиент + количество + цена)
3. Нажимает «Провести накладную» → `DeliveryService.register()`:
   - Сохраняет Delivery и DeliveryItems
   - Для каждой позиции вызывает `InventoryService.registerPurchase()`:
     - Увеличивает остаток ингредиента на количество
     - **Пересчитывает средневзвешенную себестоимость (Weighted Average Cost):**
       ```
       new_avg = (old_qty × old_avg + qty × price) / (old_qty + qty)
       ```
   - Каскадно пересчитывает себестоимость всех блюд, использующих эти ингредиенты, через `MenuService.recalcAllAffectedBy()`
4. На странице «Меню» в столбце «Себест.» сразу обновлённые значения

### 4.3. Сценарий «Резерв с проверкой пересечений»

1. Admin → Резервы → «Новый резерв»
2. Вводит гостя, выбирает стол, выбирает время (DateTimePicker), указывает количество гостей
3. Жмёт «Сохранить» → `ReservationService.save()`:
   - Проверяет: гостей ≤ вместимости стола
   - Запрашивает `findOverlapping()` — есть ли ACTIVE резерв на этот же стол в окне ±2 часа
   - Если есть → бросает `IllegalStateException("На этот стол уже есть резерв в диапазоне ±2 ч")` → UI ловит и показывает Notification
   - Если нет — сохраняет, и если время близкое (в пределах 2 часов), ставит столу статус RESERVED

## 5. Главные технические решения и почему именно так

### 5.1. Зачем JOIN FETCH в репозиториях

`Order.table` и `Order.waiter` — `LAZY` (стандарт для `@ManyToOne`). Когда сервис в `@Transactional` возвращает Order, прокси привязан к **внутренней tx-сессии**. После выхода из метода сессия закрывается, доступ к `.getTable().getTableNumber()` в UI кидает `LazyInitializationException`. `spring.jpa.open-in-view=true` не спасает, потому что прокси «помнит» уже закрытую сессию.

**Решение:** в `OrderRepository.findFirstByTableAndStatus()`, `findByStatus()`, `findWithItems()` использую JPQL с `JOIN FETCH o.table JOIN FETCH o.waiter` — Hibernate сразу подгружает связанные сущности, прокси инициализированы внутри tx и работают и после её закрытия.

То же самое для `DeliveryRepository.findAllByOrderByDeliveryDateDesc()` — там были `Delivery.items` LAZY, грид падал на `d.getItems().size()`.

### 5.2. Зачем KitchenBroadcaster и UI.access()

Vaadin Flow работает по модели request-response. По умолчанию изменения на сервере отображаются у пользователя только при следующем UI-событии (клике). Чтобы POS видел изменения с KDS **в реальном времени** (когда повар нажал «Готово»), нужен server push:

- `@Push` в `AppShell.java` включает WebSocket-канал
- `KitchenBroadcaster` (`@Component` с `CopyOnWriteArrayList<Listener>`) — собственная шина событий
- В `onAttach` каждого view регистрирую listener
- В `onDetach` отписываюсь, чтобы не утечь
- Когда сервис меняет статус блюда, бросает event → listener в POSView через `ui.access(() -> { refreshTables(); })` обновляет грид

`UI.access()` важен — broadcaster может быть вызван из любого потока (например, из @Async), а изменения UI должны быть синхронизированы с сессией Vaadin.

### 5.3. Зачем @Version на Order (Optimistic Locking)

Сценарий конфликта: официант редактирует заказ, в этот момент кухня меняет статус блюда. Без блокировки последний `commit` затирает чужие изменения.

`@Version private Long version` на `Order` включает оптимистическую блокировку Hibernate:
- При update Hibernate добавляет `WHERE id=? AND version=?`
- Если строка не найдена (версия не совпала) — `OptimisticLockException`
- Версия инкрементируется автоматически

В UI оборачиваем в try/catch и при конфликте показываем «Запись была изменена другим пользователем, обновите страницу».

### 5.4. Зачем @Validated + @Valid на сервисах

Bean Validation работает на entity-уровне через Hibernate Validator (при `save()` Hibernate валидирует и кидает `ConstraintViolationException`). Но это срабатывает поздно — на flush к БД. Хочется отлавливать раньше.

Решение: `@Validated` на классе `@Service` + `@Valid` на параметрах методов. Тогда Spring AOP-прокси валидирует параметры до входа в метод. Если пришёл `Employee` с пустым `firstName` — исключение сразу, до любых запросов к БД.

Плюс это защищает от обхода UI (если кто-то напишет тест или REST-контроллер вызывающий сервис напрямую).

### 5.5. Зачем GlobalErrorHandler

Без него `LazyInitializationException`, `NullPointerException` и прочие неожиданные ошибки сваливаются на пользователя как **полный stacktrace** в модальном окне Vaadin — ужасный UX и потенциальная утечка деталей реализации.

`GlobalErrorHandler` — `@Component implements VaadinServiceInitListener`:
- Регистрируется в каждой Vaadin-сессии
- Распознаёт `ConstraintViolationException`, `IllegalStateException`, `IllegalArgumentException` → показывает осмысленное сообщение
- Всё остальное → «Внутренняя ошибка, обратитесь к администратору» + полный stacktrace в SLF4J-лог
- Никаких stacktrace в UI

### 5.6. Зачем soft-delete (статусы) вместо DELETE

- **Сотрудник** → статус `FIRED` (не DELETE) — потому что есть заказы и смены с FK на него
- **Заказ** → статус `CANCELLED` — потому что есть payments, история нужна для отчётности
- **Блюдо** → `isActive=false` — потому что в `OrderItem` есть FK
- **Тех-карта** — единственное реальное удаление (FK только в одну сторону, нет историй)

Это даёт:
1. Целостность данных (нет orphaned ссылок)
2. Аудит и отчётность (вся история сохранена)
3. Восстановление случайных удалений (просто меняешь статус обратно)

### 5.7. Зачем JPA-наследование (нет в проекте), почему отдельные таблицы

Каждая сущность — своя таблица. Не используем JPA-наследование (`@Inheritance`), потому что в предметной области нет иерархий типа «Employee → Manager extends Employee». `Role` — это enum-атрибут, не подкласс.

## 7. Безопасность — детально

### Аутентификация
- `AppUserDetailsService implements UserDetailsService` загружает Employee по логину
- Проверяет статус ≠ FIRED (уволенный не войдёт даже с правильным паролем)
- Пароль хешируется через `BCryptPasswordEncoder` — это адаптивный хеш с автогенерацией соли, устойчив к rainbow-table и brute-force на современных GPU

### Авторизация
- **Защита маршрутов на двух уровнях:**
  1. `SecurityConfig` через `VaadinSecurityConfigurer` — все маршруты требуют авторизации по умолчанию
  2. `@RolesAllowed` на каждом view — какие роли могут зайти
- Если waiter введёт `/admin/employees` в адресной строке → Spring Security возвращает «Access is denied by annotations on the view» (видно на скриншоте `14-access-denied.png`)
- `LoginView` помечен `@AnonymousAllowed`

### Защита от типичных атак
- **CSRF** — встроен в Vaadin Security (токены в URL/headers, проверка при каждом POST)
- **SQL Injection** — невозможен, потому что всё через JPA с prepared statements
- **XSS** — Vaadin escape'ит весь текст автоматически (нет innerHTML, есть только text content)
- **Password leak в логах** — нигде не логируется поле `passwordHash`

### Что НЕ реализовано (специально упомяну если спросят)
- Rate limiting на логине (можно добавить через bucket4j)
- 2FA
- Аудит-журнал входов
- Forgot password (есть кнопка, но скрыта `setForgotPasswordButtonVisible(false)`)

## 8. Развёртывание через Docker

### Структура
- `Dockerfile` — двухстадийная сборка:
  - **Stage 1 `build`** — `maven:3.9-eclipse-temurin-21` — компилирует jar
  - **Stage 2 `runtime`** — `eclipse-temurin:21-jre-jammy` — только JRE + jar, ~250 MB
  - Запускается под непривилегированным юзером `spring`
- `docker-compose.yml` — два сервиса:
  - `mysql` (image `mysql:8.4`) — `healthcheck` через mysqladmin ping
  - `app` (build from Dockerfile) — `depends_on: mysql.condition: service_healthy`
- `taverna-mysql-data` — volume для постоянного хранения данных БД
- `taverna-net` — bridge-сеть, контейнеры обращаются по имени (`jdbc:mysql://mysql:3306/...`)

### Конфигурация через env-переменные
- `.env.example` — шаблон, юзер копирует в `.env` и заполняет
- `application-prod.properties` использует placeholders `${SPRING_DATASOURCE_URL:...}` — можно менять адрес БД без пересборки

### Одна команда для запуска
```bash
docker compose up -d --build
```

## 9. Что было сложного и как решилось

### 9.1. LazyInitializationException на POSView после повторного клика
**Симптом:** клик по столу с открытым заказом не открывал OrderDialog, в логах `LazyInitializationException: RestaurantTable#1`.
**Корень:** `OrderRepository.findFirstByTableAndStatus()` отдавал Order с lazy proxy на table. После закрытия @Transactional прокси «orphaned».
**Решение:** JOIN FETCH в JPQL-запросе.

### 9.2. Аналогичная проблема на DeliveriesView в проде с MySQL
**Симптом:** «Внутренняя ошибка» при заходе в «Накладные».
**Корень:** грид рендерил `d.getItems().size()`, items LAZY.
**Решение:** добавил JOIN FETCH в `DeliveryRepository.findAllByOrderByDeliveryDateDesc()`.

### 9.3. KitchenBroadcaster глотал исключения
**Симптом:** иногда KDS переставал обновляться без видимой причины.
**Корень:** в `broadcast()` был `catch (Exception ignored)` — все ошибки терялись.
**Решение:** заменил на `log.warn("...", ex)` — fan-out не прерывается, но ошибки видны в логах.

### 9.4. ReservationService разрешал двойные брони
**Симптом:** можно было забронировать один стол на одно время дважды.
**Решение:** добавил метод `findOverlapping` с JPQL и проверку окна ±2 часа в сервисе.

### 9.5. Оплата могла дважды посчитать платёж
**Корень:** в `OrderService.pay()` сохранял payment через `payments.save(p)`, потом стрим по `managed.getPayments()` — Hibernate мог рефрешнуть коллекцию и last payment попадал дважды.
**Решение:** явный `managed.getPayments().add(p)` перед save — синхронизация коллекции.

## 10. Возможные вопросы защиты и ответы

### «Почему Vaadin, а не React/Angular?»
- Один язык — Java и на сервере, и на UI. Меньше context-switching.
- Меньше шаблонного кода: нет API endpoints, DTO mapping, axios-вызовов, redux-стора.
- Бизнес-логика не размазана по двум кодовым базам, всё в одном репо.
- Минусы Vaadin честно: тяжелее стандартный React (больше Java-памяти на сессию), не подходит для SEO-страниц. Для внутреннего ERP-инструмента ресторана — идеален.

### «Почему MySQL, а не PostgreSQL?»
- MySQL — стандарт де-факто для веб-приложений, проще найти DBA/хостинг.
- Для предметной области проекта (CRUD + транзакции) нет фич PostgreSQL, которые были бы критичны.
- Можно поменять на Postgres минимальными правками: сменить driver, dialect, URL.

### «Почему Hibernate, а не JdbcTemplate?»
- ORM сокращает boilerplate: вместо `ResultSet.getString("name")` — просто `entity.getName()`.
- Транзакции, lazy loading, dirty checking — из коробки.
- Минус: нужно знать как Hibernate работает (LazyInit, N+1, JOIN FETCH).

### «Что будет при 1000 одновременных заказов?»
- Узкое место — MySQL и WebSocket-соединения Vaadin.
- В текущей конфигурации (HikariCP pool 10 соединений) — выдержит ~50-100 conccurrent.
- Масштабирование: увеличить pool, добавить read-replica MySQL, поставить sticky sessions перед несколькими instance'ами app.
- Для маленького-среднего ресторана (5-10 столов, 2-3 официанта) — over-engineered уже сейчас.

### «Почему open-in-view=true? Это же anti-pattern!»
- Согласен, в большом проекте — anti-pattern (рендеринг страницы держит соединение к БД).
- Для нашего размера (small app) — упрощает разработку, не нужно везде писать DTO.
- Производительность всё равно ограничена пользователями (50-100 одновременных), а не БД.
- В будущем можно вынести в DTO, отключить OSIV, но это работа на день.

### «Почему ddl-auto=update? Это опасно в проде»
- Согласен в долгосрочной перспективе.
- Сейчас используем для прототипа — Hibernate сам синхронизирует схему с моделью.
- При выходе в реальный продакшен надо перейти на Liquibase или Flyway: каждое изменение схемы — отдельная миграция в репозитории, версионируется в Git, накатывается контролируемо.

### «Где у вас тесты?»
- Есть smoke-test `TavernaApplicationTests` через `@SpringBootTest` + H2 — проверяет, что контекст поднимается, репозитории инициализируются, DataInitializer срабатывает.
- Проводил **ручное E2E-тестирование через Playwright**: логин → POS → заказ → KDS → оплата → проверка ролей → проверка валидации. 10 тестовых сценариев в таблице 6.3 отчёта.
- Что хотелось бы добавить: unit-тесты для сервисов с Mockito, integration-тесты с Testcontainers (поднимающие настоящий MySQL).

### «Почему нет ролевой матрицы в отдельной таблице?»
- Sumple: 4 фиксированные роли (ADMIN, WAITER, CHEF, BARTENDER), новые роли добавлять редко.
- Роль — поле `enum` в `Employee`, не отдельная таблица.
- Если потребуется динамическое управление правами (как Keycloak), можно вынести в `Role` + `Permission` + `RolePermission` таблицы. Сейчас overkill.

### «Почему вы не используете микросервисы?»
- Микросервисы оправданы при размере команды >10 человек, нагрузке >10К RPS, разных скоростях деплоя сервисов.
- Здесь — монолит из 75 классов, одна команда (один разработчик). Микросервисы дадут только overhead: дополнительные деплои, distributed transactions, network latency.

### «Что такое `@Transactional(propagation = REQUIRED)` и почему он по умолчанию?»
- `REQUIRED` — если уже есть транзакция в стеке вызовов, метод присоединяется к ней; иначе создаётся новая.
- Это безопасный дефолт: все методы внутри одного сервиса разделят одну транзакцию, rollback атомарный.
- Альтернативы: `REQUIRES_NEW` (всегда новая, как для логирования), `NESTED` (вложенная в savepoint).

### «Что произойдёт, если упадёт MySQL во время оплаты?»
- Транзакция откатится автоматически: `Payment` не сохранится, `Order.status` не изменится, стол не освободится.
- Hibernate бросит `JpaSystemException`, `GlobalErrorHandler` поймает и покажет «Внутренняя ошибка».
- Когда MySQL поднимется — официант повторит оплату, дублей не будет.

### «Что такое CSRF и как от него защищаетесь?»
- CSRF (Cross-Site Request Forgery) — атакующий заставляет залогиненного юзера выполнить нежелательное действие через подделанный запрос с другого сайта.
- Vaadin Security ставит CSRF-токены на каждый запрос автоматически (X-CSRF-TOKEN header или скрытое поле). Без правильного токена POST не принимается.
- Дополнительно — все мутирующие операции идут через WebSocket internal channel, который завязан на session id.
